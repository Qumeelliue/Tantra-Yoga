# Заметка: Pi Coding Agent — какие паттерны реально забирать

> Источник: разбор статьи про агентный harness Pi (автор — Mario Zechner,
> создатель libGDX). Извлекаем переносимое, отсекая полемику.

## Зачем это в проекте

Наш проект развивает свою агентную практику (опенсорсный harness + навыки-скиллы).
Заметка фиксирует, какие принципы из Pi стоит внедрять, а какие — отклонять,
чтобы не тянуть в проект раздувание контекста и «кораблей».

## Что брать (переносимые паттерны)

1. **Тонкое ядро вместо раздутого промпта.** Минимальный системный промпт
   (< 1000 токенов) дал Pi измеримый выигрыш в Terminal-Bench 2.0 против Claude Code
   (~10k токенов). Каждый токен промпта — сигнал или шум; шум деградирует фокус.
2. **Lazy / dynamic tool loading.** Грузить инструменты лениво (по надобности),
   а не класть все описания в каждый запрос. Аналог в нашем стеке — скиллы,
   которые подключаются по совпадению с задачей, а не вшиты в каждый контекст.
3. **Split tool results.** Одна порция результата — модели, другая — UI.
   Не всё, что показывает интерфейс, нужно модели (и наоборот).
4. **Древовидные JSONL-сессии (/tree, /fork, /share).** Состояние разговора —
   версионируемый лог (как git для мышления), переносимый между провайдерами
   и сессиями.
5. **Расширения вместо утолщения ядра.** «Ask the agent to build it» → расширение
   на TypeScript (jiti) → перезагрузка → инструмент вырос. Ядро не толстеет,
   всё новое живёт в расширениях и скиллах.

## Где статья лукавит (не брать как догму)

- **«Субагент посреди сессии — признак плохого планирования» — спорно.** Субагент
  с отдельным контекстом — это изоляция мусора, а не шум: делегируем, получаем
  сжатый результат, экономия контекста главного потока (не раздувание).
- **«Permission popup'ы — security theater» — позиция автора для собственного CLI.**
  Для инструментов с реальным доступом (деньги, деплой) гейты — страховка, а не театр.
- **MCP-оверхед (13–18k токенов) реален**, но решение — ленивая загрузка, а не отказ.
- **Минимум промпта ≠ безопасность.** У Claude Code и у нас промпт большой не только
  из-за шума: там safety-инварианты (антиджайлбрейк, ограничения на коммиты/секреты).
  Срезать их до нуля — перенести ответственность на саму модель.

## Практический вывод для проекта

Паттерн «тонкое ядро + расширения + ленивая загрузка» — брать.
Догму «минимум = хорошо» — не брать. Минимум, который всё ещё держит
безопасность и гигиену контекста, — золотая середина.
